<p>关于 Claude API 要不要住宅出口，讨论常常停在要不要这一层，很少有人往下问为什么。这篇用五个连续的问题往下推：平台到底看不看出口、成功率掉在哪一环、住宅出口能改善什么、成本怎么摆平、什么时候该换方案。每个问题给一个可验证的判断方法，而不是一句结论。</p>

<h2>一、问题一：平台到底看不看出口 IP</h2>
<p>先给一个不讨巧的答案：看，但不是唯一依据。任何对外服务都会记录源地址，这是基础设施层面的常规操作。问题在于这个信号在决策里的权重有多大，以及在什么情况下会被放大。</p>
<h3>地址是成本最低的初筛信号</h3>
<p>对平台来说，判断一个请求来自机房还是住宅，只需要查一次 ASN，成本几乎为零。所以它一定会被用在初筛环节：不是直接拒绝，而是决定这个请求要不要接受更严格的检查。这就解释了为什么有些团队换了地址之后体感立刻变好，也解释了为什么另一些团队换了之后毫无变化。</p>
<h3>初筛之后看的是行为</h3>
<p>过了初筛，权重就交给行为特征：请求频率、并发曲线、失败重试模式、请求体的一致性。这一层与地址类型无关，也是很多换了地址还是不行的情况的真正原因。判断方法很简单：把请求频率降到正常水平再看，如果问题消失，说明原本是行为问题。</p>
<h3>所以结论是看，但不只看</h3>
<p>把出口当成唯一变量，会陷入反复换供应商的循环；完全忽略出口，又会在需要长期稳定身份的场景里吃亏。正确的做法是把它当成一个可以调节的输入，而不是决定成败的开关。</p>

<h2>二、问题二：成功率掉在哪一环</h2>
<p>成功率低是一个结果，不是一个原因。把一次调用拆成四段，分别统计，才知道该修哪里。这一步做不做，决定了后面所有排查是有的放矢还是碰运气。</p>
<h3>四段拆法</h3>
<p>域名解析、TCP 与 TLS 握手、请求发送与首字节、响应流式接收。四段各自统计成功率和耗时，任何一段明显偏低，就是问题所在。多数人只统计最后一段，所以永远找不到原因，只能看到一个笼统的失败率。</p>
<h3>超时设置会把网络问题伪装成业务问题</h3>
<p>客户端超时设得过紧，正常的网络抖动就会被记成失败。流式响应尤其明显：首字节很快，但整体读取超过默认超时，就会在最后几秒被切断。这类失败在日志里和真实故障长得一样，只有把耗时分布画出来才能区分。</p>
<h3>重试策略会放大失败数字</h3>
<p>失败一次重试三次，日志里的失败数变成四倍，看起来像大面积故障。统计时要按业务请求去重，而不是按 HTTP 请求计数，否则你会为一个不存在的问题加班。</p>

<h2>三、问题三：住宅出口能改善什么、不能改善什么</h2>
<p>把能力边界说清楚，比列举优点有用。住宅出口改善的是来源看起来像普通用户，它不改变你的请求内容和请求节奏。</p>
<h3>能改善的部分</h3>
<p>初筛环节的通过率、长期同一身份的一致性、以及在与账号绑定的场景里减少环境突变。这三项对有真实用户身份的链路影响明显，也是这类投入的主要回报来源。</p>
<h3>不能改善的部分</h3>
<p>配额限制、请求体错误、模型不可用、并发超限，这些和出口无关。用住宅出口去解 429，等于用错工具，还会让你误以为问题已经解决。</p>
<h3>可能变差的部分</h3>
<p>住宅线路的抖动通常大于机房线路，如果业务对延迟极敏感而对外观不敏感，换住宅出口反而会降低体验。这是必须承认的代价，也是选型时最容易被忽略的一项。</p>

<h2>四、问题四：成本和收益怎么摆平</h2>
<p>住宅出口的价格通常是机房出口的数倍，所以要问清楚：多出来的钱买到了什么，这个收益能不能被量化。量化不了，就很难在预算会上说清楚。</p>
<h3>把收益换算成可比的单位</h3>
<p>如果出口改善让失败率从百分之五降到百分之一，省下的是重试流量和人工排查时间。把这个折算成月度金额，再和差价比较，结论会很清晰。人工时间的单价按团队实际成本算，不要用行业平均值糊弄自己。</p>
<h3>按账号而不是按请求算</h3>
<p>与身份相关的场景，成本应该摊到账号上：每个账号每月的出口成本是多少，这个账号带来的价值是多少。按请求摊，会低估长尾账号的成本，也会让决策偏向于砍掉小账号。</p>

<h2>五、问题五：什么时候该换方案</h2>
<p>换方案要有触发条件，否则会变成情绪化决策。下面几条是可以直接写进运维手册的硬条件，达到就评估，达不到就别折腾。</p>
<h3>成功率连续低于基线</h3>
<p>连续七天低于基线的九成，且排除账号与请求体问题后仍然如此，就该评估替换。单日波动不算，因为网络本来就有波动，按单日决策会让你一年换十家。</p>
<h3>替换频率超出承受能力，或业务形态变了</h3>
<p>一个月内地址被迫更换超过两次，说明这家供应商的地址质量或上游稳定性不达标，这时候谈价格没有意义。另一种情况是业务本身变了：从单账号变成多账号、从网页变成接口、从境内团队变成跨时区协作，任何一种变化都可能让原来的方案不再匹配。方案要跟着业务走，不是反过来。</p>

<h2>常见问答</h2>
<h3>住宅出口能提高 Claude API 的额度吗？</h3>
<p>答：不能。额度由账号层级与官方政策决定，与出口类型无关。换出口不会改变配额，只可能改变初筛环节的通过情况。</p>
<h3>机房出口是不是一定不能用？</h3>
<p>答：不是。内部工具、离线评测、服务端批处理这类场景，机房出口完全够用，成本也更低。是否需要用住宅出口，取决于链路上有没有需要长期保持一致的用户身份。</p>
<h3>成功率多少算正常？</h3>
<p>答：没有统一标准，要看你的基线。稳定的业务线通常在九成五以上，含大量重试的场景会低一些。关键是和自己的历史比，而不是和别人的宣传数字比。</p>
<h3>换供应商能一次解决所有问题吗？</h3>
<p>答：通常不能。供应商只影响网络这一段，账号状态、请求体、并发策略都不在其中。先把链路分段统计做出来，再决定要不要换。</p>
